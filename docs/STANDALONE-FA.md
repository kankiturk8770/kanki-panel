# تانل مستقل کانکی: دو سرور، بدون پنل، گام‌به‌گام

> همان موتور تانل پنل (نسخهٔ 2.9، روش‌های `dual` / `hq` / `h2`) را می‌توان بدون پنل و بدون دیتابیس اجرا کرد.
> هر سرور یک فایل JSON دارد و یک سرویس systemd که با بوت بالا می‌آید و خودش دوباره وصل می‌شود.
> اگر پنل دارید، همین تانل را از صفحهٔ **Tunnels › + Tunnel** بسازید؛ موتور یکی است.

```text
 کاربر ──TCP/UDP──► Node A (سرور داخل، "entry")  ══ تانل رمزشده ══►  Node B (سرور خارج، "exit") ──► مقصد
                    پورت‌هایی که کاربر وصل می‌شود                    پورت‌هایی که به آن‌ها می‌رسد
```

## ۱. جهت اتصال را انتخاب کنید

| روش | چه کسی اتصال را می‌سازد | `mode` در هر دو فایل |
|-----|--------------------------|----------------------|
| **Forward** (پیش‌فرض) | Node A به Node B وصل می‌شود؛ B گوش می‌دهد | `"direct"` |
| **Reverse** | Node B به Node A وصل می‌شود؛ A گوش می‌دهد | `"reverse"` |

اول Forward را امتحان کنید. اگر اتصال از داخل به خارج روی ۴۴۳ بریده یا کند می‌شود، Reverse را امتحان کنید.
نمونه‌ها: `docs/examples/node-a-entry.json` و `node-b-exit.json` (Forward)، `node-a-entry-reverse.json` و `node-b-exit-reverse.json` (Reverse).

## ۲. یک رمز مشترک بسازید

```bash
openssl rand -hex 24
```

همین مقدار را در `"token"` هر دو فایل بگذارید. بدون رمز مشترک، هیچ دست‌تکانی انجام نمی‌شود، و نمونه‌ها را بدون تغییر هم برنامه قبول نمی‌کند.

## ۳. فایل‌ها را ویرایش کنید

| فیلد | معنی |
|------|------|
| `role` | `"entry"` = سروری که کاربران به آن وصل می‌شوند (Node A) · `"exit"` = سروری که به مقصدها می‌رسد (Node B) |
| `transport` | `"dual"` (پیشنهادی: اول QUIC با ماسک، اگر UDP رد نشد خودکار HTTP/2) · `"hq"` · `"h2"` · و روش‌های قدیمی `tcpmux`، `wss`، `cdn`... |
| `port` | پورتی که سمت گوش‌دهنده باز می‌کند (مثلاً `443`) |
| `remote` | سمت وصل‌شونده: `"آدرس-سرور-مقابل:443"` |
| `conns` | تعداد لینک موازی (۴ خوب است) |
| `sni`, `host`, `path` | نام نمایش‌داده‌شده در دست‌تکانی TLS و درخواست HTTP (چند نام را با ویرگول بنویسید) |
| `frag` | `true`: ClientHello در بسته‌های ریز می‌رود (در برابر فیلترهایی که SNI را سرجمع نمی‌کنند) |
| `tcp`, `udp` | پورت‌های منتقل‌شونده، فقط در فایل entry: `"8443:443"` یعنی «روی A پورت ۸۴۴۳ را بگیر و به پورت ۴۴۳ مقصد برسان». بازه هم می‌شود: `"1000-1005"` |
| `target` | فقط در exit: مقصد روی سرور B (پیش‌فرض `127.0.0.1`) |

## ۴. نصب (اول Node B، بعد Node A)

روی هر سرور، اسکریپت و فایل JSON همان سرور را بگذارید و:

```bash
sudo bash install-standalone.sh /root/tunnel.json
```

اسکریپت: برنامه را از آخرین انتشار دانلود و با checksum بررسی می‌کند (بدون checksum نصب نمی‌کند)، فایل را قبل از هر تغییر در سیستم کنترل می‌کند،
کاربر سیستمی بدون shell می‌سازد، سرویس `kanki-tunnel-run` را فعال می‌کند و (اگر ufw روشن باشد) پورت‌ها را باز می‌کند.

سروری که به GitHub دسترسی ندارد: فایل `kanki-panel` را با `scp` ببرید و بزنید:

```bash
sudo KANKI_BIN=/root/kanki-panel bash install-standalone.sh /root/tunnel.json
```

**فایروال:** در حالت Forward، روی B باید هم `443/tcp` و هم `443/udp` باز باشد (`dual` هر دو را می‌خواهد). اگر ارائه‌دهندهٔ سرور فایروال جدا دارد، آنجا هم باز کنید.

## ۵. بررسی کار می‌کند یا نه

```bash
systemctl status kanki-tunnel-run
journalctl -u kanki-tunnel-run -f
```

هر ۱۰ ثانیه وضعیت بررسی می‌شود و هر وقت چیزی عوض شده باشد (با ترافیک تقریباً همیشه) یک خط چاپ می‌شود، مثلاً `a-to-b [dual] links 4/4 rtt 38 ms ...`. **`links 4/4`** یعنی هر چهار لینک بالا است.
بعد از آن، از یک دستگاه به پورت گرفته‌شدهٔ A وصل شوید (مثلاً `ssh -p 2222 user@A`) و ببینید به B می‌رسد.

اگر `links 0/4` ماند، آخر همان خط `last error:` دلیل را می‌گوید. رایج‌ترین‌ها: فایروال (TCP یا UDP بسته)، رمز دو سمت یکی نیست، آدرس `remote` اشتباه است.

## ۶. نگهداری

| کار | دستور |
|-----|-------|
| تغییر تنظیمات | فایل `/etc/kanki-tunnel-run/tunnel.json` را ویرایش و `systemctl restart kanki-tunnel-run` |
| به‌روزرسانی برنامه | دوباره همان دستور نصب (آخرین انتشار را می‌گیرد) |
| توقف موقت | `systemctl stop kanki-tunnel-run` |
| حذف سرویس (تنظیمات می‌ماند) | `sudo bash install-standalone.sh --uninstall` |
| حذف کامل | `sudo bash install-standalone.sh --purge` |

اتصال خودکار: هر لینک که قطع شود با تأخیر ۱ تا ۱۰ ثانیه دوباره ساخته می‌شود، لینک بی‌حرکت بعد از ۳۰ ثانیه کنار گذاشته می‌شود، QUIC هر ۵ ثانیه پینگ می‌فرستد و systemd اگر خود برنامه بمیرد بعد از ۲ ثانیه دوباره بالایش می‌آورد (بدون محدودیت تعداد تلاش).

## ۷. گواهی TLS

پیش‌فرض گواهی خودامضا است و مشکلی ندارد: اعتبار اصلی را رمز مشترک و دست‌تکانی داخل تانل تأمین می‌کند. اگر گواهی واقعی می‌خواهید (`"cert"` و `"key"` در فایل exit)، فایل‌ها باید برای کاربر سرویس خوانا باشند
و زیر `/home` یا `/root` نباشند (سرویس آن‌ها را نمی‌بیند). مثلاً آن‌ها را در `/etc/kanki-tunnel-run/` بگذارید و `chgrp kanki-tunnel-run` و `chmod 640` کنید.

## ۸. حد و مرزها (صادقانه)

* هیچ تانلی «غیرقابل شناسایی» نیست. این طراحی ردپای ثابت (بایت ثابت، اندازهٔ ثابت، امضای QUIC) را از بین می‌برد و شبیه وب می‌شود، ولی تحلیل آماری یا فهرست سفید آدرس‌ها هنوز می‌تواند اثر بگذارد.
* TLS شبیه مرورگر است ولی اثر انگشت دقیق Chrome (JA3/JA4) را کتابخانهٔ rustls نمی‌تواند عیناً بسازد.
* این تانل پورت‌های TCP و UDP را منتقل می‌کند، رابط TUN/TAP لایهٔ ۳ نیست. برای رابط لایهٔ ۳، در پنل نوع تانل **AmneziaWG** را انتخاب کنید، گزینهٔ «Hide it inside a transport» را روشن کنید و transport را `dual` بگذارید.
